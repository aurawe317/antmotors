# 登录与注册加固方案（Antoto）

> 制定日期：2026-10-03
> 背景：平台从 1 家租户扩展到 4 家、员工从 1 人到 9 人，当天即出现"登录成功却秒掉"、"换设备登不上"、"同一操作时好时坏"等故障。
> 已确认的架构前提：**一个账号只属于一家公司**（不需要跨公司成员关系与公司切换）。

---

## 一、根因判断（重要）

**故障不是"人变多"造成的。** 4–5 名新增用户没有让系统变慢，也没有增加复杂度。

真正的原因是：**当前认证是自建的**（自己签 token、自己维护 `tokens` 表、自己用 PBKDF2 算密码）。这套东西没有经过真实多用户场景检验，今天被首次完整触发。

因此加固的目标不是"扩容"，而是**消除单点故障、让失败可观测**。

---

## 二、现状缺陷清单（均为实测，非推测）

| # | 缺陷 | 已发生的故障 | 严重度 |
|---|---|---|---|
| 1 | token 存在数据库表里，签发/校验都查表 | `tokens` 表被清空 → **全部公司同时掉线** | 极高 |
| 2 | token 写入失败被静默吞掉 | 登录"成功"→ 下一个请求必 401 → 反复掉线 | 极高 |
| 3 | 登录查找不带 `company_id` | 跨公司 ID 撞名 → 登进别家 | 高 |
| 4 | ID 唯一性只有应用层校验 | 并发注册可绕过 | 高 |
| 5 | 邮箱/手机号格式不统一 | 手机号永远匹配不上完整邮箱 | 中 |
| 6 | 忘记密码依赖邮件往返 | 未建 Auth 账号的员工 → 死锁 | 中 |
| 7 | 无登录限流 | 可被暴力破解 | 高 |
| 8 | 无认证审计日志 | 故障只能靠猜，无法定位 | 中 |
| 9 | 会话无状态视图 | 无法查看/踢出某台设备 | 低 |

---

## 三、目标架构

```
                 ┌──────────────────────────────┐
  登录 / 注册  →  │  认证层（本次加固的重点）      │
                 │  · 无状态 HMAC token（不查库）  │
                 │  · 登录限流 + 审计            │
                 │  · 统一账号解析（ID / 邮箱）   │
                 └──────────────┬───────────────┘
                                │ 校验通过 → 得到 {empId, companyId}
                 ┌──────────────▼───────────────┐
                 │  业务层（几乎不变）            │
                 │  车辆 / 门店 / 员工 / 会员      │
                 └──────────────────────────────┘

  数据库中：tokens 表降级为「审计/吊销用途」，不再是登录的必需品
```

**核心思想**：**登录态不再依赖数据库里的一行记录。** 只要签名密钥在，任何一次"数据库出意外"都不会让人登不上。

---

## 四、分阶段实施

### 阶段 1（P0）消除单点故障 — 预计 1 天

**1.1 无状态 token**

```
token = base64url(payload) + "." + hmacSha256(payload, SECRET)
payload = { e: 员工ID, c: 公司ID, x: 过期时间戳 }
```

服务端只做两件事：**验签** + **查是否过期**。不查 `tokens` 表。

**降级保护**（必须）：
- 若环境变量 `TOKEN_SECRET` 未配置 → 自动回退到现有 `tokens` 表逻辑
- 保证任何阶段部署都不会导致无法登录

**验收标准（可自测）**：
```sql
delete from public.tokens;   -- 模拟最坏情况
```
执行后，**所有已登录用户继续正常使用**，且能正常登录新设备。

**1.2 密钥管理**
- `TOKEN_SECRET` 存 Cloudflare 环境变量（Production + Preview 都要）
- 生成方式：随机 32 字节，base64 编码
- **禁止**写进代码仓库

---

### 阶段 2（P1）安全基础 — 预计 1 天

| 项 | 说明 | 验收 |
|---|---|---|
| **登录限流** | 同一账号/同一 IP 连续失败 5 次 → 锁定 15 分钟 | 暴力破解被挡住 |
| **审计日志** | 新表 `auth_events`：登录成功/失败/登出/密码重置，含 IP 与时间 | 故障可追溯 |
| **密码强度** | 注册/改密强制 ≥8 位且非纯数字 | 弱密码被拒 |
| **ID 数据库唯一约束** | 执行已提供的 `supabase-schema-employee-unique-id.sql` | 跨公司重名不可能 |
| **账号解析统一** | ID / 邮箱 / 手机号规范化后统一入口 | 手机号能登录 |

---

### 阶段 3（P2）可运维 — 预计 0.5 天

- 「我的」页增加"登录设备"列表，可**踢出**某台设备
- 登录历史（时间、IP、设备）供老板查阅
- `admin.html` 增加"重置员工密码"入口（后端接口 `POST /api/employee/reset-password` 已完成，只差 UI）

---

## 五、每阶段的回滚策略

**三个阶段互相独立，可单独回滚。**

- 阶段 1：关掉 `TOKEN_SECRET` 环境变量 → 自动退回旧逻辑
- 阶段 2：各项独立，可分别关闭
- 阶段 3：纯增量，删掉 UI 即回滚

**任何阶段上线后都要用真实请求验证**（今天教训：`node --check` 查不出运行时错误）。

## 六、运维手册

### 日常
- 没有任何日常操作。系统上线后应保持"零维护"。

### 密钥轮换（建议每年一次，或怀疑泄露时）
1. 生成新 `TOKEN_SECRET`
2. 更新 Cloudflare 环境变量
3. 所有人都需要重新登录一次（**这是预期行为，提前通知**）

### 应急：有人忘记密码
- 老板在 App 内为员工重置（阶段 3 后可用）
- 当前已可用接口：`POST /api/employee/reset-password`（需 boss 账号）

### 应急：怀疑密钥泄露
1. 立即更换 `TOKEN_SECRET` → 所有会话失效（安全优先）
2. 查 `auth_events` 审计日志确认影响范围

## 七、中期备选：迁移 Supabase Auth

**暂不执行**，但记录决策依据：

- **收益**：密码哈希、邮件重置、邮箱验证、OAuth 全部由官方维护，RLS 真正生效
- **成本**：迁移 9 个现有账号、迁移期需双轨运行（老 token 与 Auth 并行）、改动面覆盖全部接口鉴权
- **触发迁移的条件**（满足任一即应启动）：
  - 需要社交登录（Google/Apple）
  - 需要邮箱验证/密码找回自助
  - 员工数超过 ~100
  - 需要真正的行级安全隔离

**结论：先做阶段 1–3。系统稳定运行一段时间后，再评估是否值得迁移。**
